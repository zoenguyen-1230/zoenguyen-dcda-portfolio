Experiment A: Portfolio Enhancement

For Experiment A, I used Claude Opus 4.5 as a coding collaborator inside VS Code to build a responsive image carousel for my portfolio. The carousel displays photos of my friends and me at TCU to highlight my campus experience. The feature includes next/previous buttons, dot navigation, keyboard arrow support, and accessible alt text.

I started with a broad “build a carousel” prompt, then refined it through debugging. The first version overflowed its container and only displayed the first image. I worked with Claude to adjust the CSS while I also manually corrected image filenames/paths and rewrote alt text so it matched my actual photos. After several rounds of feedback and testing, I successfully implemented a fully functional carousel that enhances the visual appeal and user experience of my portfolio. The final code is clean, well-commented, and adheres to best practices for responsive design and accessibility.

Vibe Coding Guidelines/Reflection

When I used AI for vibe coding, I try to treat it as a collaborator rather than an autopilot. I start by planning the feature first and listing the exact behaviors and constraints I want, so my prompt is specific enough and make room for less errors. After the AI generates code, I read through every section before running it, and I test it section by section so I can see which changes actually affect the result. I use an “understanding spectrum” in my comments to honestly mark what I fully understand, what I understand at a logic level, and what I still find unclear. When something breaks, I debug step by step, from checking file paths, layout rules, to data flow, instead of assuming the whole solution is wrong. I also make content-level corrections myself, such as updating image names, paths, and alt text, to ensure accuracy and accessibility. Overall, my guideline is to let AI build the foundation of the code, but keep responsibility for verification, clarity, and final decisions to myself.

Experiment B: Python Map Visualization (Using Google Colab + Gemini)

San Francisco Restaurant Inspection Scores Map

Download my Google Colab notebook (.ipynb)  |  Download the dataset (.csv)

The deliverables include my Colab notebook (.ipynb), the original dataset (.csv), and a HTML file of the final interactive map view on my portfolio repository.

For Experiment B, I used Google Colab with Gemini 2.5 Flash (embedded in Colab) as an AI coding collaborator to create an interactive map visualization of San Francisco restaurant inspection scores. The dataset comes from the City of San Francisco (found on Kaggle) and includes inspection records, scores, risk categories, and coordinates. My goal was to create a map of the latest inspection per restaurant, color markers by score (red → yellow → green), and include detailed popups (restaurant name, address, score, date, and risk breakdown). I also wanted a heatmap layer for low scores and toggleable views showing “Best scores” vs “Worst scores.”

The first AI-generated version worked but revealed practical issues when tested: some popups displayed NaN values, some rows with no values were plotted, and the map was visually cluttered due to heavy marker overlap. I used follow-up prompts to clean the dataset (i.e., dropping missing coordinates and scores), replace missing text fields with “Unknown,” and modify the map to reduce clutter using marker limits, clustering, smaller radius scaling, and transparency tuning. I validated each change by rerunning cells and visually checking the output map rather than assuming correctness from code alone.

Original AI prompts I used:

  • Initial build prompt: “This is a dataset from the City of San Francisco of restaurants' inspection score in the city. help me build a map visualization of the latest inspection per restaurant, colored by inspection score (red → yellow → green). Popup shows name, address, score, date, and risk breakdown. Include a heatmap layer for low scores, and show toggle views of “Best scores” vs “Worst scores” as separate layers.”
  • Cleaning prompt (NaNs + invalid points): “The map is looking good, but I'm seeing NaN values in the popup and some points shouldn’t be plotted. Please modify my code so that rows with NaN latitude, longitude, or inspection_score are excluded, and NaN text does not appear in popups or tooltips, missing fields are replaced with “Unknown” instead of NaN in labels. Show me the cleaned pandas filtering step and the safer popup formatting step. Keep everything else the same and explain each change briefly.”
  • Decluttering prompt (overlapping markers): “The map is too visually cluttered because there are too many markers overlapping. Please refactor my code to reduce clutter while keeping it analytically useful. Update it to keep only the latest inspection per restaurant, limit to the top N most recent or lowest-score inspections (config variable like MAX_MARKERS), keep MarkerCluster but improve readability, reduce marker radius scaling so circles overlap less, add transparency tuning. Show the modified code block only.”

Gemini’s initial output successfully generated the overall Folium mapping structure (map setup, marker coloring, and popups), but in early versions I noticed two practical issues:

  • Some popups/tooltips displayed literal NaN text when fields were missing.
  • The map was visually crowded, with overlapping markers making it hard to interpret patterns.

Those issues pushed me to refine the pipeline by filtering out invalid rows and improving popup formatting, then adding a marker limit and clustering strategy to keep the map readable.

Vibe Coding Guidelines/Reflection

When using AI for Python and visualization tasks, I treat it as a collaborator rather than a pure code generator. I start by defining the goal and output features clearly in my prompt, including visual behavior and data-cleaning requirements. After AI generates code, I run it in small sections and verify outputs step by step, especially with maps where visual errors reveal data issues quickly. I document where code works but my understanding is partial, and I make comments marking what I fully understand versus what I only understand briefly. When results look wrong, such as NaN popups or overcrowded markers, I follow up with AI with specific problems instead of asking for a total rewrite. I also keep make sure I check the output myself for validation, filtering rules, and labeling decisions.
